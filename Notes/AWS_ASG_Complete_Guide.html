🤔 What Problem Does Auto Scaling Solve?

Traditional infrastructure is provisioned for peak load — which means you are either over-provisioned (paying for capacity you don't use) or under-provisioned (your application crashes during traffic spikes).

Scale Out (Add)

Horizontal Scale Out
📉

Section 2 — Launch Templates & Launch Configurations 0:10 – 0:25

📋 What is a Launch Template?

A Launch Template (LT) is a blueprint that defines the EC2 instance configuration. When ASG needs to launch a new instance, it uses the Launch Template to know exactly what kind of instance to create.


What a Launch Template Defines

  • AMI ID — Which OS image to use (Amazon Linux, Ubuntu, custom AMI)
  • Instance Type — t3.micro, t3.medium, m5.large, etc.
  • Key Pair — For SSH access to instances
  • Security Groups — Firewall rules (port 80, 22, 443)
  • IAM Instance Profile — Role for the EC2 instance
  • User Data Script — Bootstrap script run on first launch
  • EBS Volume Configuration — Size, type (gp3, io2), encryption
  • Network Interfaces — VPC, subnet settings
  • Tags — Metadata applied to launched instances
  • Placement Group — HPC cluster, spread, partition

⚔️ Launch Template vs Launch Configuration — What's the Difference?

⚠️
Always use Launch Templates! AWS has stopped adding new features to Launch Configurations. For all new ASGs, use Launch Templates. Migrate existing Launch Configurations to Launch Templates as soon as possible.

Section 3 — Creating an Auto Scaling Group 0:25 – 0:45

🔢 The Three Capacity Settings — MIN, MAX, DESIRED

ASG Capacity Settings Explained: ┌──────────────────────────────────────────────────────────┐ │ │ │ MIN = 2 ←── NEVER go below this │ │ MAX = 10 ←── NEVER go above this │ │ DESIRED = 4 ←── Target right now (adjustable by policies)│ │ │ │ Scaling OUT: DESIRED increases (up to MAX) │ │ Scaling IN: DESIRED decreases (down to MIN) │ │ │ │ ▓▓ [Instance 1] AZ-1a (always running: MIN=2) │ │ ▓▓ [Instance 2] AZ-1b (always running: MIN=2) │ │ ▒▒ [Instance 3] AZ-1a (DESIRED=4, currently up) │ │ ▒▒ [Instance 4] AZ-1b (DESIRED=4, currently up) │ │ ░░ [Slot 5-10] (available if MAX allows) │ │ │ └──────────────────────────────────────────────────────────┘ Rule: MIN <= DESIRED <= MAX (always true)

🔒

Minimum Capacity

The floor. ASG will never have fewer instances than this, even at zero demand. Set to the minimum needed for high availability (usually 2+ for prod).

Safety Floor
🔝

Maximum Capacity

The ceiling. ASG will never launch more instances than this. Prevents runaway scaling (and runaway costs!) from bugs or attacks.

Cost Guard
🎯

Desired Capacity

The target right now. ASG actively maintains this number. Scaling policies adjust desired capacity up or down within min/max limits.

Current Target

🌍 Multi-AZ Configuration — High Availability by Design

ASG distributes instances evenly across multiple Availability Zones. If one AZ goes down, instances in other AZs keep serving traffic.


Region: ap-south-1 ┌──────────────────────────────────────┐ │ ASG: WebServer-ASG (Desired: 6) │ │ │ │ ┌───────────────┐ ┌───────────────┐ ┌───────────────┐│ │ │ AZ: 1a │ │ AZ: 1b │ │ AZ: 1c ││ │ │ │ │ │ │ ││ │ │ [Instance 1] │ │ [Instance 2] │ │ [Instance 3] ││ │ │ [Instance 4] │ │ [Instance 5] │ │ [Instance 6] ││ │ │ │ │ │ │ ││ │ └───────────────┘ └───────────────┘ └───────────────┘│ │ │ │ If AZ-1a FAILS → ASG launches │ │ 2 more in AZ-1b and AZ-1c │ └──────────────────────────────────────┘
ℹ️
AZ Rebalancing: When an AZ comes back online after an outage, ASG performs rebalancing — launching instances in the recovered AZ and terminating excess instances in overloaded AZs to maintain even distribution.
✅
Best Practice: Always span at least 3 AZs for production workloads. Use private subnets for the ASG instances and let ALB in public subnets handle incoming traffic.

💻 Creating an ASG via CLI

BASH — Complete ASG Creation
# ── Create the Auto Scaling Group ──────────────────────────────────── aws autoscaling create-auto-scaling-group \ --auto-scaling-group-name "WebServer-ASG" \ --launch-template "LaunchTemplateName=WebServer-LT,Version=\$Latest" \ --min-size 2 \ --max-size 10 \ --desired-capacity 4 \ --vpc-zone-identifier "subnet-abc123,subnet-def456,subnet-ghi789" \ --health-check-type ELB \ --health-check-grace-period 300 \ --target-group-arns "arn:aws:elasticloadbalancing:us-east-1:123:targetgroup/my-tg/abc123" \ --tags "Key=Name,Value=WebServer-ASG,PropagateAtLaunch=true" \ "Key=Environment,Value=Production,PropagateAtLaunch=true" # ── Describe the ASG ────────────────────────────────────────────────── aws autoscaling describe-auto-scaling-groups \ --auto-scaling-group-names "WebServer-ASG" # ── Manually adjust desired capacity ────────────────────────────────── aws autoscaling set-desired-capacity \ --auto-scaling-group-name "WebServer-ASG" \ --desired-capacity 6 # ── List all instances in the ASG ──────────────────────────────────── aws autoscaling describe-auto-scaling-instances \ --query 'AutoScalingInstances[?AutoScalingGroupName==`WebServer-ASG`]' # ── Delete the ASG ──────────────────────────────────────────────────── aws autoscaling delete-auto-scaling-group \ --auto-scaling-group-name "WebServer-ASG" \ --force-delete # Terminates all running instances first

🏥 Health Checks — How ASG Monitors Instance Health

Health Check TypeWhat It ChecksWhen to UseFrequency
EC2 (Default)Is the EC2 instance in "running" state? Are hardware/hypervisor checks passing?Simple setups without a load balancerEvery ~5 minutes
ELB (ALB/NLB)Is the instance passing the ALB health check endpoint? (e.g., HTTP 200 from /health)Web applications with an ALB in frontConfigurable (e.g., 30s)
Custom (VPC Lattice)Custom health probe via VPC Lattice serviceService mesh architecturesConfigurable

ℹ️
Health Check Grace Period: After a new instance launches, ASG waits this many seconds before starting health checks. Set it long enough for your app to fully start (e.g., 300 seconds for Spring Boot apps). Too short = instances killed before they're ready!
⚠️
Unhealthy Instance Flow: Instance fails health check → ASG marks it unhealthy → ASG launches a replacement → After replacement is healthy → Unhealthy instance is terminated automatically.

Section 4 — Scaling Policies 0:45 – 1:10

🎛️ Overview — The 4 Types of Scaling Policies

🎯 1. Target Tracking Scaling

The easiest and most recommended policy. You set a target metric value and ASG automatically adjusts capacity to keep the metric at that target.


Example: "Keep average CPU at 50%"

ASG = Like a thermostat — it adds/removes capacity automatically to maintain the target.

Recommended for most cases

📶 2. Simple Scaling

A CloudWatch alarm triggers a single scaling action. After the action, there's a cooldown period before the next action can occur.


Example: "If CPU > 80% for 5 min, add 2 instances, cooldown 300s"

Reactive and simple, but can be slow to respond during fast spikes.

Simple / legacy workloads

📏 3. Step Scaling

Like simple scaling but smarter — scale by different amounts based on how much the metric is breached. No cooldown between steps.


Example: CPU 70-80% → add 1, CPU 80-90% → add 3, CPU >90% → add 5

Responds more aggressively to severe breaches.

Variable load patterns

📅 4. Scheduled Scaling

Scale at specific dates and times. Use when you know in advance when load will increase or decrease.


Example: "Every Monday 9 AM, scale to 10 instances. Every Friday 6 PM, scale down to 2"

Perfect for predictable patterns — business hours, weekly reports, etc.

Predictable schedules

🎯 Target Tracking Scaling — Deep Dive

Target Tracking is like a cruise control system for your infrastructure. You set the speed (metric target), and ASG adjusts the "throttle" (instance count) automatically.


Available Predefined Metrics

MetricDescriptionTypical TargetUse Case
ASGAverageCPUUtilizationAverage CPU % across all instances in the ASG40–70%CPU-intensive apps (web servers, APIs)
ASGAverageNetworkInAverage network bytes received per instanceApp-specificNetwork-heavy apps (media streaming)
ASGAverageNetworkOutAverage network bytes sent per instanceApp-specificContent delivery, uploads
ALBRequestCountPerTargetRequests per second per target in ALB Target Group100–1000 req/sWeb apps with ALB in front
💡
You can also use custom CloudWatch metrics with Target Tracking. For example, track SQS queue depth to scale workers, or a custom latency metric from your application.

BASH — Create Target Tracking Policy
# ── Target Tracking: Keep CPU at 50% ───────────────────────────────── aws autoscaling put-scaling-policy \ --auto-scaling-group-name "WebServer-ASG" \ --policy-name "CPU-Target-50-Percent" \ --policy-type TargetTrackingScaling \ --target-tracking-configuration '{ "PredefinedMetricSpecification": { "PredefinedMetricType": "ASGAverageCPUUtilization" }, "TargetValue": 50.0, "ScaleInCooldown": 300, "ScaleOutCooldown": 60, "DisableScaleIn": false }' # ── Target Tracking: ALB Request Count (500 requests/target) ────────── aws autoscaling put-scaling-policy \ --auto-scaling-group-name "WebServer-ASG" \ --policy-name "ALB-Request-Count-Policy" \ --policy-type TargetTrackingScaling \ --target-tracking-configuration '{ "PredefinedMetricSpecification": { "PredefinedMetricType": "ALBRequestCountPerTarget", "ResourceLabel": "app/my-alb/abc123/targetgroup/my-tg/def456" }, "TargetValue": 500.0, "ScaleOutCooldown": 60, "ScaleInCooldown": 300 }' # ── Target Tracking: Custom Metric (SQS Queue Depth) ────────────────── aws autoscaling put-scaling-policy \ --auto-scaling-group-name "Worker-ASG" \ --policy-name "SQS-Queue-Depth-Policy" \ --policy-type TargetTrackingScaling \ --target-tracking-configuration '{ "CustomizedMetricSpecification": { "MetricName": "ApproximateNumberOfMessagesVisible", "Namespace": "AWS/SQS", "Dimensions": [{"Name": "QueueName", "Value": "my-job-queue"}], "Statistic": "Average" }, "TargetValue": 100.0 }'

📏 Step Scaling — Deep Dive

Step Scaling Configuration Example: ────────────────────────────────────────────────────────────── SCALE OUT (Add instances when CPU is HIGH): ┌─────────────────────────────┬────────────────────────────┐ │ Metric Breach │ Action │ ├─────────────────────────────┼────────────────────────────┤ │ CPU >= 60% and < 70% │ Add 1 instance │ │ CPU >= 70% and < 85% │ Add 2 instances │ │ CPU >= 85% │ Add 4 instances (URGENT!) │ └─────────────────────────────┴────────────────────────────┘ SCALE IN (Remove instances when CPU is LOW): ┌─────────────────────────────┬────────────────────────────┐ │ Metric Breach │ Action │ ├─────────────────────────────┼────────────────────────────┤ │ CPU <= 30% and > 20% │ Remove 1 instance │ │ CPU <= 20% │ Remove 2 instances │ └─────────────────────────────┴────────────────────────────┘ Key: No cooldown between steps — responds faster!

BASH — Step Scaling Policy
# Step 1: Create a CloudWatch alarm for high CPU aws cloudwatch put-metric-alarm \ --alarm-name "WebServer-HighCPU" \ --metric-name CPUUtilization \ --namespace AWS/EC2 \ --statistic Average \ --period 60 \ --evaluation-periods 2 \ --threshold 60 \ --comparison-operator GreaterThanOrEqualToThreshold \ --dimensions Name=AutoScalingGroupName,Value=WebServer-ASG \ --alarm-actions "arn:aws:autoscaling:us-east-1:123:scalingPolicy:abc:autoScalingGroupName/WebServer-ASG:policyName/ScaleOut-Step" # Step 2: Create the Step Scaling Policy (Scale Out) aws autoscaling put-scaling-policy \ --auto-scaling-group-name "WebServer-ASG" \ --policy-name "ScaleOut-Step" \ --policy-type StepScaling \ --adjustment-type ChangeInCapacity \ --step-adjustments '[ {"MetricIntervalLowerBound": 0, "MetricIntervalUpperBound": 10, "ScalingAdjustment": 1}, {"MetricIntervalLowerBound": 10, "MetricIntervalUpperBound": 25, "ScalingAdjustment": 2}, {"MetricIntervalLowerBound": 25, "ScalingAdjustment": 4} ]'

📅 Scheduled Scaling — Deep Dive

🏢 Business Hours Example

An e-commerce company knows traffic follows a predictable pattern: high during business hours (9 AM–9 PM) and low overnight. Instead of waiting for auto-scaling to react, they pre-scale at scheduled times — faster response, guaranteed capacity.


BASH — Scheduled Scaling Actions
# ── Scale UP every Monday-Friday at 8:30 AM (before business opens) ── aws autoscaling put-scheduled-update-group-action \ --auto-scaling-group-name "WebServer-ASG" \ --scheduled-action-name "Scale-Up-Business-Hours" \ --recurrence "30 3 * * 1-5" \ --min-size 4 \ --max-size 20 \ --desired-capacity 8 # ── Scale DOWN every day at 10 PM (after business closes) ───────────── aws autoscaling put-scheduled-update-group-action \ --auto-scaling-group-name "WebServer-ASG" \ --scheduled-action-name "Scale-Down-Overnight" \ --recurrence "30 16 * * *" \ --min-size 2 \ --max-size 6 \ --desired-capacity 2 # ── One-time scale for a product launch event ────────────────────────── aws autoscaling put-scheduled-update-group-action \ --auto-scaling-group-name "WebServer-ASG" \ --scheduled-action-name "ProductLaunch-Scale" \ --start-time "2026-09-01T00:00:00Z" \ --min-size 20 \ --desired-capacity 20 \ --max-size 50 # Note: Times are in UTC. # IST is UTC+5:30, so 8:30 AM IST = 03:00 UTC

❄️ Cooldown Periods — Preventing Thrashing

A cooldown period is a pause after a scaling activity, during which ASG does not launch or terminate additional instances. This gives the system time to stabilize before another scaling action occurs.


Cooldown Visualization: ───────────────────────────────────────────────────────────── TIME: 0s 60s 120s 180s 240s 300s │ │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ ▼ CPU: 88% ──── 65% ──── 55% ──── 48% ──── 52% ──── 45% ◀─Scale Out!─▶ ◀─── 300s Cooldown Period ───────▶ ◀─ OK to scale again Without cooldown: ASG would scale out MULTIPLE times during the spike! With cooldown: One scale-out, then wait and observe — much more stable. Recommended Cooldown Values: - Scale OUT cooldown: 60-120 seconds (respond fast to spikes) - Scale IN cooldown: 300-600 seconds (be conservative, don't scale in too fast)

Section 5 — ASG + ALB Integration 1:10 – 1:25

🔗 How ASG Works with Application Load Balancer

ASG and ALB work together to provide a fully elastic, highly available architecture. ASG controls the fleet of EC2 instances, while ALB distributes traffic intelligently across them.


Internet Traffic Architecture with ASG + ALB: Internet Users │ ▼ ┌─────────────────────────────────────────────────────────────┐ │ Application Load Balancer (ALB) │ │ Public Subnets | Multi-AZ | Port 80/443 │ │ │ │ Listener: HTTP:80 → Redirect to HTTPS │ │ Listener: HTTPS:443 → Forward to Target Group │ └─────────────────┬───────────────┬───────────────────────────┘ │ │ ┌────────┘ └────────┐ ▼ ▼ ┌─────────────────┐ ┌─────────────────┐ │ AZ: 1a │ │ AZ: 1b │ │ Private Subnet │ │ Private Subnet │ │ │ │ │ │ [Instance 1] ←─┼─ Registered │ [Instance 2] ←─┼─ Registered │ [Instance 3] ←─┼─ in Target │ [Instance 4] ←─┼─ in Target │ │ Group │ │ Group │ Launching... │ │ Launching... │ │ [Instance 5] ──►│─ Registering │ [Instance 6] ──►│─ Registering └─────────────────┘ └─────────────────┘ ↑ ASG auto-registers new instances with ALB Target Group ↑ ASG auto-deregisters terminated instances before shutdown

✅
Auto Registration: When ASG launches a new instance, it automatically registers it with the ALB Target Group. No manual intervention needed. The ALB starts sending traffic only after the health check passes.
ℹ️
Connection Draining (Deregistration Delay): Before terminating an instance, ALB waits for existing connections to complete (default: 300 seconds). This ensures no requests are dropped during scale-in.

Section 6 — Lifecycle Hooks, Warmup & Termination Policies 1:25 – 1:40

🔄 ASG Instance Lifecycle — Full State Machine

Instance Launch Lifecycle: ────────────────────────────────────────────────────────────────── Pending ──────────────► Pending:Wait ──────────────► Pending:Proceed │ │ │ │ (No hook) │ (Lifecycle Hook active) │ │ │ Run: install agents, │ │ │ configure monitoring, │ │ │ pre-warm caches │ │ │ │ └────────────────────────┴──────────────────────────────┘ │ ▼ InService ◄────── ALB health check passes │ ┌────────────────┘ │ (Scale-in / health check failure) ▼ Terminating ──────► Terminating:Wait ──────────► Terminating:Proceed │ │ │ (Lifecycle Hook active) │ │ Run: drain connections, │ │ flush logs, deregister, │ │ backup state │ │ │ └──────────────────────────────┘ │ ▼ Terminated

⚓ Lifecycle Hooks — Custom Actions During Launch/Termination

Lifecycle Hooks pause the instance in a wait state, giving you time to run custom scripts or logic before the instance becomes active or gets terminated.


🚀

Launch Hook (Pending:Wait)

Run BEFORE instance starts serving traffic. Use to:

  • Install monitoring agents (Datadog, NewRelic)
  • Pull and warm up application caches
  • Register with service discovery (Consul)
  • Run security compliance checks
  • Pull latest config from Parameter Store
Max wait: 48 hours
🛑

Terminate Hook (Terminating:Wait)

Run BEFORE instance is deleted. Use to:

  • Gracefully drain active connections
  • Flush application logs to S3
  • Deregister from service discovery
  • Backup in-memory state / session data
  • Send notifications to monitoring systems
Max wait: 48 hours

BASH — Create Lifecycle Hook
# ── Create a Launch Lifecycle Hook ──────────────────────────────────── aws autoscaling put-lifecycle-hook \ --auto-scaling-group-name "WebServer-ASG" \ --lifecycle-hook-name "install-agents-hook" \ --lifecycle-transition "autoscaling:EC2_INSTANCE_LAUNCHING" \ --default-result ABANDON \ --heartbeat-timeout 300 \ --notification-metadata '{"action": "install-monitoring-agent"}' # ── Create a Termination Lifecycle Hook ─────────────────────────────── aws autoscaling put-lifecycle-hook \ --auto-scaling-group-name "WebServer-ASG" \ --lifecycle-hook-name "drain-connections-hook" \ --lifecycle-transition "autoscaling:EC2_INSTANCE_TERMINATING" \ --default-result CONTINUE \ --heartbeat-timeout 120 # ── Complete the hook from the instance (signal success) ────────────── aws autoscaling complete-lifecycle-action \ --auto-scaling-group-name "WebServer-ASG" \ --lifecycle-hook-name "install-agents-hook" \ --instance-id i-1234567890abcdef0 \ --lifecycle-action-result CONTINUE

🌡️ Instance Warmup Period

The Instance Warmup period tells ASG how long to wait after launching a new instance before considering it for scaling metrics. During warmup, the new instance is excluded from scaling calculations.


☕ The New Hire Analogy

When a new developer joins the team, you don't immediately measure their productivity on Day 1. You give them a ramp-up period (warmup) to learn the codebase. Only after they're fully up to speed do you include them in team velocity metrics. ASG warmup works the same way — don't count new instances in metrics until they're ready.

⚠️
Set warmup correctly! If warmup is too short, ASG may see high CPU from new instances that are still initializing and launch even MORE instances unnecessarily (a scaling "storm"). Default is 300s. Adjust based on your app's startup time.

🗑️ Termination Policies — Which Instance Gets Killed First?

When ASG scales in, it must decide which instances to terminate. Termination policies control this selection order.


PolicyBehaviorBest For
DefaultAWS's built-in algorithm: balance AZs first, then use OldestLaunchTemplate, then OldestInstanceMost workloads
OldestInstanceTerminate the instance that has been running longestWhen you want fresh instances regularly
NewestInstanceTerminate the most recently launched instanceRolling back a bad deployment
OldestLaunchTemplateTerminate instances using the oldest Launch Template versionAfter a template update — clean up old instances
ClosestToNextInstanceHourTerminate instance closest to its next billing hour (saves money)Cost-sensitive workloads
AllocationStrategyAlign with Spot allocation strategy to optimize cost/availabilityMixed On-Demand + Spot ASGs

Instance Protection: You can mark specific instances as "protected from scale in" using aws autoscaling set-instance-protection. Useful for instances running long-running jobs that must complete before termination.

🏆 ASG Best Practices

🏗️ Architecture

  • Span ASG across at least 3 AZs in production
  • Use Launch Templates — never Launch Configurations
  • Make instances stateless — store state in RDS/DynamoDB/S3
  • Use ALB health checks (not EC2) when behind a load balancer
  • Set a health check grace period longer than app startup time
  • Use private subnets for ASG instances, ALB in public subnets
  • Bake AMIs with pre-installed app (faster launch vs userdata)

💰 Cost Optimization

  • Use Spot Instances in Mixed Instance Policy (up to 90% savings)
  • Set conservative scale-in cooldowns to avoid thrashing
  • Use Scheduled Scaling for predictable patterns
  • Use Target Tracking for automatic right-sizing
  • Enable detailed monitoring (1-min intervals) for faster scaling
  • Set appropriate minimum capacity — don't over-provision the floor
  • Use AWS Compute Optimizer for right-sizing recommendations

🚀 Mixed Instances Policy — Spot + On-Demand

Use a combination of On-Demand and Spot instances within a single ASG to optimize for cost while maintaining availability.


Mixed Instances Policy Example: ───────────────────────────────────────────────────────────────── ASG Config: ├── On-Demand Base Capacity: 2 (always guaranteed, no interruptions) ├── On-Demand Percentage: 20% (of instances above base) └── Spot Percentage: 80% (cost savings! potentially interrupted) Example with 10 total instances: ├── 2 On-Demand instances (base) ├── 2 On-Demand instances (20% of remaining 8) └── 6 Spot instances (80% of remaining 8) ← Up to 90% cheaper! Multiple Instance Types (Spot Pool Diversity): ├── t3.large (primary) ├── t3a.large (alternative) ├── m5.large (alternative) └── m5a.large (alternative) → If one Spot type is unavailable/interrupted, use another pool!

BASH — Mixed Instance ASG
aws autoscaling create-auto-scaling-group \ --auto-scaling-group-name "MixedInstance-ASG" \ --min-size 2 \ --max-size 20 \ --desired-capacity 6 \ --vpc-zone-identifier "subnet-1a,subnet-1b,subnet-1c" \ --mixed-instances-policy '{ "LaunchTemplate": { "LaunchTemplateSpecification": { "LaunchTemplateName": "WebServer-LT", "Version": "$Latest" }, "Overrides": [ {"InstanceType": "t3.large"}, {"InstanceType": "t3a.large"}, {"InstanceType": "m5.large"}, {"InstanceType": "m5a.large"} ] }, "InstancesDistribution": { "OnDemandBaseCapacity": 2, "OnDemandPercentageAboveBaseCapacity": 20, "SpotAllocationStrategy": "capacity-optimized" } }'

🎯 Exam Tips — Most Frequently Tested ASG Concepts

✅ Must Know Facts

  • ASG is free — charges are for EC2 instances only
  • Always use Launch Templates, not Launch Configurations
  • Target Tracking is simplest and most recommended
  • Health check grace period = time before checks begin
  • Instance warmup = time before metrics are counted
  • Use ELB health check when behind an ALB
  • Lifecycle hooks pause the instance lifecycle
  • Spot + On-Demand Mix achieves up to 90% cost savings

⚠️ Common Gotchas

  • MIN <= DESIRED <= MAX — always maintain this rule
  • Instances must be stateless — local data lost on termination
  • Cooldown prevents scaling; Warmup excludes from metrics
  • Default health check is EC2 — change to ELB for web apps
  • Launch Configuration is immutable — must create new one
  • Scheduled scaling uses UTC time, not local time
  • ASG spans multiple AZs but lives in one Region
  • Scale-in protection prevents individual instances from being terminated
