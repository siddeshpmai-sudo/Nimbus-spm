Section 1 — Introduction to AWS IAM 0:00 – 0:10

🤔 What is AWS IAM?

AWS Identity and Access Management (IAM) is a free global AWS service that lets you control who (authentication) can do what (authorization) on which AWS resources, and under what conditions.


🙋

Authentication — WHO?

Verifying the identity of a person or service trying to access AWS resources. (Username + Password, Access Keys)

Identity Verification
🔑

Authorization — WHAT?

Determining which AWS services and resources an authenticated identity can access and what actions they can perform.

Permission Control
📝

Auditing — WHAT DID?

AWS CloudTrail records every API call made in your account — who did what, when, and from where.

Activity Tracking

🏢 Real-World Analogy — The Office Building

🏙️ Think of AWS as a Corporate Office Building
  • AWS Account = The entire office building (you own it)
  • Root User = The building owner with MASTER keys — lock it away, never use daily
  • IAM User = An employee with a personal badge (username + password)
  • IAM Group = A department (Engineering, Finance, HR) — all members share same access
  • IAM Role = A temporary contractor badge — given for a specific job, expires after use
  • IAM Policy = The access control rules — which floors, rooms, and equipment are accessible
  • STS = The front desk that issues temporary visitor badges

🌍 Key Characteristics of IAM

  • IAM is a Global Service — not tied to any specific region
  • IAM is completely FREE — no additional charges ever
  • Supports Multi-Factor Authentication (MFA)
  • Integrates with every single AWS service natively
  • Follows the Principle of Least Privilege by design
  • Supports Identity Federation (Google, LDAP, SAML)
  • Uses JSON for all policy documents
  • Provides CloudTrail integration for full audit trails
  • Supports up to 5,000 users per account
  • Integrates with AWS Organizations via SCPs
⚠️
Critical Root Account Warning: The root account has UNLIMITED access to your entire AWS account and cannot be restricted by IAM policies. NEVER use it for daily tasks. Immediately after creating your account: (1) Enable MFA on root, (2) Create an IAM admin user, (3) Never create root access keys.

Section 2 — IAM Users 0:25 – 0:35

👤 What is an IAM User?

An IAM User is an entity in AWS that represents a specific person or application. Each user has a unique name within the AWS account and their own set of security credentials that are permanent (unlike roles).


Two Types of Access Credentials

🖥️

Console Access (Human Users)

Uses a Username + Password to log into the AWS Management Console web interface. Can optionally be protected with MFA for extra security.

Human Users
⚙️

Programmatic Access (Apps/Scripts)

Uses Access Key ID + Secret Access Key pair for AWS CLI, SDK, and API calls. The Secret Key is only shown ONCE at creation time.

Applications / CI-CD

🚨
Never hardcode Access Keys! Never embed Access Key ID and Secret Access Key directly in code, scripts, or configuration files that get committed to version control. Use IAM Roles for applications running on AWS services.

🧪 Creating an IAM User — Step by Step (Console)

1
Navigate: AWS Console → IAM → Users → Click "Create User" button
2
User Name: Enter a descriptive name like devops-alice. Name must be unique in the account.
3
Select AWS Access Type: Check "Provide user access to AWS Management Console" for console access, enable programmatic access for CLI/API
4
Set Permissions: Option A: Add to a Group | Option B: Copy from existing user | Option C: Attach policies directly
5
Tags (Optional): Add key-value tags like Department=DevOps, Project=Nimbus for organization
6
Review and Create: Download the CSV file — contains the access key credentials. This is the ONLY time you can view the secret access key!

Section 3 — IAM Groups 0:35 – 0:45

👥 What is an IAM Group?

An IAM Group is a collection of IAM users. Instead of attaching policies to each user individually, you attach policies to the group — all users in the group automatically inherit those permissions.


🏢 The Department / Team Analogy

Instead of programming each employee's keycard individually, you create a "DevOps Team" access template. Everyone in the DevOps team automatically gets EC2 + S3 + CloudWatch access. When Alice joins DevOps, add her to the group — she instantly gets all DevOps permissions. When Bob leaves DevOps, remove him — permissions are instantly revoked. No need to touch individual user policies!


⚠️
Groups CANNOT contain other groups. IAM does NOT support nested groups. A group can only contain users. However, one user CAN be a member of multiple groups (up to 10 groups per user). Permissions from all groups are combined.

🏗️ Typical Group Structure in a Tech Organization

AWS Account (Your Organization) ├── 👥 Group: Admins │ ├── 📜 Policy: AdministratorAccess (Full AWS access) │ └── 👤 Users: alice (CTO), john (Cloud Architect) │ ├── 👥 Group: DevOps │ ├── 📜 Policy: AmazonEC2FullAccess │ ├── 📜 Policy: AmazonS3FullAccess │ ├── 📜 Policy: CloudWatchFullAccess │ └── 👤 Users: bob, carol, dave │ ├── 👥 Group: Developers │ ├── 📜 Policy: AWSLambdaFullAccess │ ├── 📜 Policy: AmazonDynamoDBFullAccess │ ├── 📜 Policy: AmazonS3ReadOnlyAccess │ └── 👤 Users: eve, frank, grace │ └── 👥 Group: Finance ├── 📜 Policy: AWSBillingReadOnlyAccess └── 👤 Users: henry, iris

💻 IAM Group Management via AWS CLI

BASH — Group Operations
# Create groups aws iam create-group --group-name Admins aws iam create-group --group-name DevOps aws iam create-group --group-name Developers # Attach AWS Managed Policy to a group aws iam attach-group-policy \ --group-name DevOps \ --policy-arn arn:aws:iam::aws:policy/AmazonEC2FullAccess aws iam attach-group-policy \ --group-name DevOps \ --policy-arn arn:aws:iam::aws:policy/AmazonS3FullAccess # Add users to groups aws iam add-user-to-group --group-name DevOps --user-name bob aws iam add-user-to-group --group-name DevOps --user-name carol # List users in a group aws iam get-group --group-name DevOps # List all groups a user belongs to aws iam list-groups-for-user --user-name bob # List policies attached to a group aws iam list-attached-group-policies --group-name DevOps # Remove a user from a group aws iam remove-user-from-group --group-name DevOps --user-name bob # Delete a group (must remove all users and policies first) aws iam detach-group-policy --group-name DevOps --policy-arn arn:aws:iam::aws:policy/AmazonEC2FullAccess aws iam delete-group --group-name DevOps

Section 4 — IAM Policies 0:45 – 1:05

📜 What is an IAM Policy?

An IAM Policy is a JSON document that formally defines permissions — what actions are allowed or denied on which AWS resources, and under what conditions. Policies are the language of authorization in AWS.


The 6 Core Elements of a Policy

ElementDescriptionExampleRequired?
VersionPolicy language version. Always use 2012-10-17"2012-10-17"✅ Yes
StatementContainer for one or more permission statements (array)[{...}, {...}]✅ Yes
Effect"Allow" or "Deny" — a Deny always overrides any Allow"Allow"✅ Yes
ActionSpecific AWS API actions using service:action format"s3:GetObject"✅ Yes
ResourceThe ARN of the AWS resource(s) the statement applies to"arn:aws:s3:::my-bucket/*"✅ Yes
ConditionOptional conditions that must be true for the statement to apply{"StringEquals": {...}}❌ Optional
SidStatement ID — optional human-readable label for the statement"AllowS3ReadAccess"❌ Optional
PrincipalEntity the policy applies to (only in resource-based policies)"arn:aws:iam::123:user/alice"Resource-based only

📝 Complete Policy JSON Examples

Example 1: Basic S3 Read Policy

JSON
{ "Version": "2012-10-17", "Statement": [ { "Sid": "AllowS3Read", "Effect": "Allow", "Action": [ "s3:GetObject", "s3:ListBucket", "s3:GetBucketLocation" ], "Resource": [ "arn:aws:s3:::my-company-bucket", "arn:aws:s3:::my-company-bucket/*" ] } ] }

Example 2: EC2 Full + S3 ReadOnly

JSON
{ "Version": "2012-10-17", "Statement": [ { "Sid": "EC2FullAccess", "Effect": "Allow", "Action": "ec2:*", "Resource": "*" }, { "Sid": "S3ReadOnly", "Effect": "Allow", "Action": [ "s3:Get*", "s3:List*" ], "Resource": "*" }, { "Sid": "DenyS3Delete", "Effect": "Deny", "Action": "s3:Delete*", "Resource": "*" } ] }

Example 3: Conditional Policy — Region Restriction

JSON — Allow EC2 only in us-east-1
{ "Version": "2012-10-17", "Statement": [ { "Sid": "AllowEC2InUSEast1Only", "Effect": "Allow", "Action": ["ec2:StartInstances", "ec2:StopInstances", "ec2:DescribeInstances"], "Resource": "*", "Condition": { "StringEquals": { "aws:RequestedRegion": "us-east-1" } } } ] }

Example 4: Deny if MFA Not Present (Force MFA Usage)

JSON — MFA Enforcement
{ "Version": "2012-10-17", "Statement": [ { "Sid": "DenyAllWithoutMFA", "Effect": "Deny", "NotAction": [ "iam:CreateVirtualMFADevice", "iam:EnableMFADevice", "iam:GetUser", "iam:ListMFADevices", "sts:GetSessionToken" ], "Resource": "*", "Condition": { "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" } } } ] }

Example 5: S3 Access Only from Specific IP (VPN/Office IP)

JSON — IP Address Restriction
{ "Version": "2012-10-17", "Statement": [ { "Sid": "AllowOnlyFromOfficeIP", "Effect": "Allow", "Action": "s3:*", "Resource": "arn:aws:s3:::secure-company-bucket/*", "Condition": { "IpAddress": { "aws:SourceIp": ["203.0.113.0/24", "198.51.100.5/32"] } } } ] }

🗂️ Types of IAM Policies

Policy TypeCreated ByReusable?LifecycleBest For
AWS Managed PolicyAWS✅ Yes — across accountsAWS manages updatesCommon use cases (S3FullAccess, etc.)
Customer Managed PolicyYou✅ Yes — within your accountYou manage itCustom business requirements
Inline PolicyYou❌ No — 1:1 relationshipDeleted with identitySpecial one-off exceptions
Resource-Based PolicyYouN/A — attached to resourceLives with resourceS3, SQS, Lambda permissions
SCP (Org Policy)AWS Org AdminApplied to OUs/accountsOrg-level lifecycleGuardrails across all accounts

💡
Resource-Based Policy Key Difference: Unlike identity-based policies, resource-based policies must include a Principal element specifying WHO can perform the actions. They are attached TO resources like S3 buckets, SQS queues, Lambda functions, etc.

⚖️ Policy Evaluation Logic — The Decision Tree

When an IAM principal makes an API call, AWS evaluates ALL applicable policies using this exact order:


Step 1: Is there an EXPLICIT DENY anywhere? → YES → ❌ ACCESS DENIED (immediate, no further evaluation) → NO → Continue to Step 2 Step 2: Is there an EXPLICIT ALLOW anywhere? → YES → ✅ ACCESS GRANTED → NO → Continue to Step 3 Step 3: IMPLICIT DENY (default) → 🚫 ACCESS DENIED (no policy said yes) Policy types checked (in priority order): 1. SCPs (AWS Organizations — hard ceiling) 2. Resource-based policies 3. Identity-based policies (User/Group/Role) 4. IAM Permission Boundaries 5. Session Policies (STS session)
🚨
Golden Rule: An explicit Deny always wins over any Allow, no matter what. AWS uses "default deny" — if no explicit Allow exists, the action is denied. This is the most tested IAM concept!

Section 5 — IAM Roles 1:05 – 1:25

🎭 What is an IAM Role?

An IAM Role is an IAM identity that has specific permissions but no permanent credentials. Instead of a username/password or access keys, roles provide temporary security credentials through AWS STS when they are "assumed" by trusted entities.


🔑 The Temporary Contractor Badge

Imagine hiring a plumber to fix pipes in your office. You don't give them a permanent employee badge. Instead, you give them a temporary contractor badge that only allows access to utility rooms for 4 hours. Once 4 hours pass, the badge expires automatically and becomes useless. This is exactly what an IAM Role does — scoped, temporary, time-limited access with no permanent credentials.


IAM Role vs IAM User — When to Use Which

ScenarioIAM UserIAM Role
Human logging into AWS Console✅ Correct choice❌ Not designed for this
EC2 instance needs to access S3❌ NEVER hardcode credentials✅ Always use a role
Lambda function accesses DynamoDB❌ Not applicable✅ Lambda Execution Role
Cross-account AWS access❌ Doesn't scale, security risk✅ Cross-Account Role
Corporate SSO / LDAP integration❌ Not possible✅ Identity Federation Role
GitHub Actions CI/CD deploying to AWS⚠️ Possible but risky (keys in secrets)✅ OIDC Role (no stored keys!)
ECS/EKS container accessing AWS services❌ Bad practice✅ Task/Service Account Role

🏗️ The Two Policies Inside Every Role

🤝

1. Trust Policy (Who Can Assume)

A JSON policy that defines WHICH entities are allowed to assume this role. Must specify a Principal. Without this, nobody can use the role.


Common Principals:

  • ec2.amazonaws.com — EC2 service
  • lambda.amazonaws.com — Lambda
  • arn:aws:iam::ACCOUNT_ID:root — Another AWS account
  • arn:aws:iam::ACCOUNT:user/alice — Specific user
Controls sts:AssumeRole
📋

2. Permission Policy (What Can Do)

The standard IAM policy (Managed or Inline) that defines WHAT actions the role can perform once assumed. Works exactly like any other policy.


Common examples:

  • AmazonS3ReadOnlyAccess
  • AmazonDynamoDBFullAccess
  • CloudWatchLogsFullAccess
  • Custom customer-managed policies
Controls what the role can do

🛠️ Creating and Using IAM Roles — Practical Examples

Use Case 1: EC2 Instance Role — Access S3 Without Hardcoded Keys

BASH — Complete EC2 Role Setup
# ── STEP 1: Write Trust Policy JSON ───────────────────────────── cat > ec2-trust-policy.json << 'EOF' { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Principal": { "Service": "ec2.amazonaws.com" }, "Action": "sts:AssumeRole" }] } EOF # ── STEP 2: Create the Role ────────────────────────────────────── aws iam create-role \ --role-name EC2-S3-ReadRole \ --assume-role-policy-document file://ec2-trust-policy.json \ --description "Allows EC2 instances to read from S3" # ── STEP 3: Attach Permissions Policy ─────────────────────────── aws iam attach-role-policy \ --role-name EC2-S3-ReadRole \ --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess # ── STEP 4: Create Instance Profile (required wrapper for EC2) ─── aws iam create-instance-profile \ --instance-profile-name EC2-S3-ReadProfile aws iam add-role-to-instance-profile \ --instance-profile-name EC2-S3-ReadProfile \ --role-name EC2-S3-ReadRole # ── STEP 5: Launch EC2 with the Role ──────────────────────────── aws ec2 run-instances \ --image-id ami-0c02fb55956c7d316 \ --instance-type t2.micro \ --iam-instance-profile Name=EC2-S3-ReadProfile # On the EC2 instance — these will work WITHOUT aws configure! # aws s3 ls ← Works! # aws s3 cp s3://bucket/ . ← Works! # aws s3 rm s3://bucket/file ← DENIED (ReadOnly!)

Use Case 2: Cross-Account Role (Account A accesses Account B)

BASH — Cross-Account Setup (run in Account B)
# In ACCOUNT B (222222222222): Create role that trusts Account A cat > cross-account-trust.json << 'EOF' { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::111111111111:root" // Trust entire Account A }, "Action": "sts:AssumeRole", "Condition": { "Bool": { "aws:MultiFactorAuthPresent": "true" } // Require MFA } }] } EOF aws iam create-role \ --role-name CrossAccountReadRole \ --assume-role-policy-document file://cross-account-trust.json aws iam attach-role-policy \ --role-name CrossAccountReadRole \ --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess # In ACCOUNT A (111111111111): User assumes the role aws sts assume-role \ --role-arn "arn:aws:iam::222222222222:role/CrossAccountReadRole" \ --role-session-name "alice-audit-session" \ --duration-seconds 3600 # Export the returned temp credentials: export AWS_ACCESS_KEY_ID="ASIA..." export AWS_SECRET_ACCESS_KEY="xxxx..." export AWS_SESSION_TOKEN="IQoJb3JpZ2..." # Now commands run in Account B as the role!

Use Case 3: Lambda Execution Role

BASH — Lambda Role Creation
# Trust policy for Lambda cat > lambda-trust.json << 'EOF' { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Principal": { "Service": "lambda.amazonaws.com" }, "Action": "sts:AssumeRole" }] } EOF # Create the Lambda execution role aws iam create-role \ --role-name MyLambdaExecutionRole \ --assume-role-policy-document file://lambda-trust.json # All Lambda functions need this for CloudWatch Logs aws iam attach-role-policy \ --role-name MyLambdaExecutionRole \ --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole # Additional permissions your Lambda needs aws iam attach-role-policy \ --role-name MyLambdaExecutionRole \ --policy-arn arn:aws:iam::aws:policy/AmazonDynamoDBFullAccess

Section 6 — MFA, Password Policy, STS & Permission Boundaries 1:25 – 1:40

📱 Multi-Factor Authentication (MFA)

MFA adds a second verification layer beyond username/password. Even if credentials are stolen, an attacker cannot log in without physical access to the MFA device.


Available MFA Device Types

TypeExampleHow it Works
Virtual MFA AppGoogle Authenticator, Authy6-digit TOTP code, refreshes every 30s
Hardware TOTP TokenGemalto token devicePhysical token generating TOTP codes
FIDO2 Security KeyYubiKey (USB/NFC)Tap/insert physical key — strongest option
Hardware Key FobAWS GovCloud specificFor government compliance requirements
✅
Enable MFA on: (1) Root account always, (2) All IAM admin users, (3) Any user with sensitive data access. This is the single most impactful security action.

🔐 IAM Password Policy

Define account-wide password complexity and rotation requirements for all IAM users. Set once, applies to everyone.


  • Minimum password length (8–128 characters)
  • Require uppercase and lowercase letters
  • Require at least one number
  • Require at least one special character (!@#$)
  • Password expiry (e.g., force change every 90 days)
  • Prevent password reuse (remember last 1–24 passwords)
  • Allow users to change their own password
  • Require admin reset after password expires
BASH — Set Password Policy
aws iam update-account-password-policy \ --minimum-password-length 14 \ --require-uppercase-characters \ --require-lowercase-characters \ --require-numbers \ --require-symbols \ --max-password-age 90 \ --password-reuse-prevention 12 \ --allow-users-to-change-password

OIDC / Social Login

🚧 IAM Permission Boundaries

A Permission Boundary is an advanced IAM feature. It is a managed policy attached to a user or role that sets the maximum permissions that user/role can ever have. The actual permissions are the INTERSECTION of identity policies and the boundary.


🏗️ The Construction Site Fence

A construction worker has permits to operate heavy machinery in the entire city. But the construction site has a fence around it. The worker can only operate machinery inside the fence, regardless of their city-wide permit. The fence is the Permission Boundary — it's the maximum possible working area, regardless of what other policies say.


Effective Permissions Formula

Effective Permissions = Identity Policy (User/Group/Role) ∩ (intersection with) Permission Boundary BOTH must allow an action for it to succeed. If Boundary allows but Policy denies → DENIED If Policy allows but Boundary denies → DENIED If both allow → ALLOWED

Primary Use Case

💡
Delegated Admin: Let a team lead create IAM users/roles for their team, but limit what permissions they can grant. The team lead can't create users with more permissions than the boundary allows — preventing privilege escalation.

Section 7 — IAM Best Practices 1:40 – 1:55

🏆 AWS Official IAM Best Practices

🔒 Security

  • Lock root account — MFA on, no access keys, never use daily
  • Create individual IAM users — never share credentials
  • Use Groups to assign permissions (not individual users)
  • Apply Principle of Least Privilege — start with nothing, add as needed
  • Enable MFA for all privileged users
  • Never embed credentials in code — use Roles for AWS services
  • Rotate access keys regularly (every 90 days at most)
  • Use IAM Access Analyzer to detect overly broad permissions
  • Enable CloudTrail in all regions for full audit trail

🚀 Operations

  • Prefer Customer Managed Policies over inline policies
  • Use Permission Boundaries for delegated administration
  • Tag all IAM entities (user, role, policy) for governance
  • Run Credential Reports monthly — audit inactive users
  • Use Access Advisor to identify and remove unused permissions
  • Remove unused users, roles, and access keys promptly
  • Use SCPs via AWS Organizations for guardrails across accounts
  • Automate IAM with Terraform / CloudFormation for consistency
  • Use OIDC roles for CI/CD — eliminate stored credentials entirely

🔍 IAM Auditing and Monitoring Tools

📊

IAM Credential Report

CSV report of ALL users and their credential status: password age, access key usage dates, MFA status, last login. Essential for compliance audits.

CLI
aws iam generate-credential-report aws iam get-credential-report \ --output text \ --query Content \ | base64 --decode
🔎

IAM Access Advisor

Shows when each AWS service was LAST accessed by a user, role, group, or policy. Identify dormant permissions. Helps right-size access.

CLI
aws iam generate-service-last-accessed-details \ --arn arn:aws:iam::123:user/alice
🔬

IAM Access Analyzer

Uses automated reasoning to identify resources in your account that are shared with external entities. Detects unintended public or cross-account access.

CLI
aws accessanalyzer create-analyzer \ --analyzer-name my-analyzer \ --type ACCOUNT

📋 IAM Complete Cheat Sheet — Quick Reference

Root Account
🔐 Lock it. MFA ON. No access keys. Never use daily.
IAM User
👤 Person or app with PERMANENT credentials (password or access keys)
IAM Group
👥 Collection of users. Attach policies to groups, not individual users.
IAM Role
🎭 TEMPORARY credentials via STS. For services, cross-account, federation.
IAM Policy
📜 JSON doc. Effect + Action + Resource [+ Condition]. Allow or Deny.
Explicit Deny
🚫 ALWAYS wins. Overrides any Allow, in any policy, anywhere.
Default Deny
🔒 No explicit Allow = Access Denied. IAM is deny-by-default.
STS
🎫 Security Token Service. Issues temp creds. Max 12hr duration.
Trust Policy
🤝 WHO can assume the role (Principal element in role's JSON)
Instance Profile
🖥️ Wrapper for IAM Role. Required to attach a role to EC2.
Permission Boundary
🚧 Maximum permission ceiling. Effective = Policy ∩ Boundary.
IAM Scope
🌍 Global Service. Not region-specific. Same IAM everywhere.
IAM Cost
✅ Completely FREE. No charges for IAM operations ever.
Max IAM Users
5,000 per account (soft limit, can request increase)
Groups per User
Max 10 groups per IAM user
Access Key Format
Permanent: AKIA... | Temporary (STS): ASIA...

🎯 Exam Tips — Most Frequently Tested IAM Concepts

✅ Must Know Truths

  • IAM is a Global service (not regional)
  • Explicit Deny always overrides explicit Allow
  • IAM is free of charge
  • Roles use STS for temporary credentials
  • EC2 needs an Instance Profile to use a role
  • Root account cannot be restricted by SCPs
  • New IAM users have NO permissions by default
  • SCPs from Organizations override IAM policies

⚠️ Common Gotchas & Trick Questions

  • Groups cannot be nested (no group of groups)
  • IAM roles are assumed, not attached to users
  • One user can be in multiple groups (max 10)
  • Permission Boundaries don't grant permissions — they limit them
  • Resource-based policies must have a Principal
  • Temporary access key IDs start with ASIA (not AKIA)
  • Session Token is required with temporary credentials
  • Access keys should never be stored in code or config files
