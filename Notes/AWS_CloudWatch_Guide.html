What is AWS CloudWatch?

🏥 Analogy — The Hospital Dashboard

Imagine a hospital ICU. Every patient has monitors showing heart rate, blood pressure, oxygen — in real time. When readings go critical, alarms sound and nurses are paged. CloudWatch is exactly that — the health monitoring system for your entire AWS infrastructure. Every service publishes vital signs (metrics), CloudWatch displays them, and alerts you when something goes wrong.

Core Pillars of CloudWatch

📈

Metrics

Numerical time-series data. CPU%, NetworkIn, RequestCount. Every AWS service publishes metrics automatically.

📝

Logs

Text-based output from applications, servers, Lambda functions, VPC Flow Logs. Searchable and filterable.

🔔

Alarms

Trigger actions when a metric crosses a threshold. Scale your ASG, send an SNS notification, stop an EC2 instance.

🗺️

Dashboards

Custom visual panels with metrics from multiple services and regions in a single view.

📈

CloudWatch Metrics — Deep Dive

Key Concepts: Namespace, Metric Name, Dimensions

ConceptWhat it meansExample
NamespaceContainer/category for metrics. Each service has one.AWS/EC2, AWS/RDS, AWS/Lambda
Metric NameWhat is being measuredCPUUtilization, NetworkIn, Errors
DimensionKey-value pair that identifies the specific resourceInstanceId=i-1234abcd
PeriodTime granularity of each data point60 seconds (1 minute) or 300 seconds (5 minutes)
StatisticsAggregation function applied over a periodAverage, Sum, Maximum, Minimum, SampleCount
ResolutionStandard (1-min min) or High-Resolution (1-second)High-res requires custom metrics agent

Important Built-In EC2 Metrics (Auto-Collected — Free)

  • ✅ CPUUtilization — % CPU used (0-100)
  • ✅ NetworkIn / NetworkOut — bytes in/out
  • ✅ NetworkPacketsIn / NetworkPacketsOut
  • ✅ DiskReadOps / DiskWriteOps
  • ✅ StatusCheckFailed — hardware/OS level failure
⚠️
Common Gotcha: EC2 does NOT report Memory Usage or Disk Space by default! These are inside the OS — AWS can't see them. You must install the CloudWatch Agent to get RAM and disk metrics.

Metric Resolution — Standard vs High-Resolution

TypeResolutionRetentionCost
Standard1-minute minimum15 monthsFree for basic metrics
High-Resolution1-second3 hours at 1-sec, then rolled up$0.30 per metric/month

Custom Metrics — Publish Your Own App Metrics

You can publish any metric from your application using the AWS CLI or SDK. Useful for business KPIs or app-specific monitoring.

PUBLISH CUSTOM METRIC VIA CLI
aws cloudwatch put-metric-data \ --namespace "MyApp/OrderService" \ --metric-name "OrdersProcessed" \ --value 142 \ --unit Count \ --dimensions Environment=Production,Service=OrderAPI
💡
Example use cases: Active user sessions, queue depth, orders per minute, login failures per hour, cache hit ratio. These custom metrics can trigger alarms just like AWS built-in metrics.

CloudWatch Logs — Centralized Log Management

Key Concepts: Log Groups, Log Streams, Log Events

CloudWatch Logs Hierarchy: Log Group: /aws/lambda/OrderProcessor ← One per application/service └── Log Stream: 2024/09/02/[$LATEST]abc123 ← One per execution/instance ├── 09:00:01 INFO: Order received: ORD-1001 ├── 09:00:02 INFO: Payment validated ├── 09:00:03 INFO: Order shipped └── 09:00:04 ERROR: Notification service timeout Log Group: /var/log/nginx/access.log ← From EC2 via CloudWatch Agent └── Log Stream: i-1234abcd5678 ← One stream per EC2 instance ├── 09:01:05 192.168.1.5 GET /api/products 200 45ms └── 09:01:06 192.168.1.5 POST /api/order 500 2340ms

Log Retention — Always Configure This!

By default, CloudWatch Logs are retained FOREVER — costing money indefinitely. Always set retention policy.

Retention PeriodRecommendation
1 day – 7 daysDevelopment environments, Lambda debug logs
30 daysStandard application logs, general debugging
90 daysSecurity logs for incident response windows
1 yearCompliance-required logs (HIPAA, SOC2)
Never expireAvoid — archive to S3 Glacier instead for long-term

CloudWatch Agent — Install on EC2 for Full Observability

ℹ️
The CloudWatch Agent runs on EC2 and collects: OS metrics (RAM, disk, process count, swap), and streams application log files to CloudWatch Logs.
1
Attach IAM Role to EC2 Create IAM role with policy: CloudWatchAgentServerPolicy. Attach to EC2 instance.
2
Install the Agent
sudo yum install amazon-cloudwatch-agent -y # Amazon Linux / RHEL sudo apt-get install amazon-cloudwatch-agent # Ubuntu/Debian
3
Configure via Wizard (Easiest Method)
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-config-wizard
The wizard asks: which metrics (CPU, RAM, disk?), which log files to collect, what log group names to use.
4
Start the Agent
sudo systemctl start amazon-cloudwatch-agent sudo systemctl enable amazon-cloudwatch-agent # start on reboot
5
Verify in Console CloudWatch → Metrics → CWAgent namespace → See mem_used_percent, disk_used_percent appearing.

CloudWatch Logs Insights — Query Logs with SQL-like Syntax

Logs Insights lets you analyze log data interactively using a purpose-built query language.

QUERY: Find all ERROR logs in last 1 hour
fields @timestamp, @message | filter @message like /ERROR/ | sort @timestamp desc | limit 50
QUERY: Count 5xx errors by minute
fields @timestamp, @message | filter @message like /5[0-9][0-9]/ | stats count(*) as errors by bin(1m) | sort @timestamp desc
QUERY: Lambda cold starts analysis
filter @type = "REPORT" | stats avg(@initDuration) as avg_cold_start, count(@initDuration) as cold_starts, max(@duration) as max_duration by bin(5m)

Metric Filters — Turn Log Data into Metrics

What is a Metric Filter?

A Metric Filter scans a CloudWatch Log Group for a specific text pattern and increments a custom metric each time it finds a match. This bridges logs and alarms.

App writes "ERROR 500" to log
→
CloudWatch Logs captures it
→
Metric Filter: count "ERROR 500" occurrences
→
Custom Metric: HTTP5xxErrors count
→
Alarm fires → SNS alert

Example: Create Metric Filter for HTTP 500 Errors

1
Go to: CloudWatch → Log Groups → select your log group → Actions → Create metric filter
2
Filter pattern: [ip, id, user, timestamp, request, status_code=5*, size] or simply "HTTP/1.1 5"
3
Metric details: Namespace: MyApp/WebServer, Metric name: HTTP5xxErrors, Value: 1, Unit: Count
4
Create alarm: On this new metric — If count >= 10 in 5 minutes → Alert the on-call team via SNS

CloudWatch Alarms — Step-by-Step Creation

Alarm States

✅

OK

The metric is within the defined threshold. Everything is normal.

🚨

ALARM

The metric has breached the threshold for the configured number of periods. Action is triggered.

❓

INSUFFICIENT_DATA

Not enough data points to evaluate the alarm (e.g., EC2 just started, metric hasn't been collected yet).

🔬 Lab: Create an EC2 CPU Alarm with SNS Notification
Goal: Alert when any EC2 instance's CPU exceeds 80% for 5 minutes
  1. Go to CloudWatch → Alarms → Create Alarm
  2. Click Select metric → EC2 → Per-Instance Metrics
  3. Find your instance, check CPUUtilization → Select metric
  4. Conditions:
    • Statistic: Average
    • Period: 1 minute
    • Threshold type: Static
    • Condition: Greater than 80
    • Datapoints to alarm: 5 out of 5 (fires only if CPU > 80% for 5 consecutive minutes)
  5. Notification: Select SNS topic → DevOps-Alerts (or create new topic with your email)
  6. Name: EC2-HighCPU-Alarm → Create alarm
  7. Test it: SSH into EC2, run stress --cpu 4 --timeout 400 → Watch alarm transition to ALARM state

Composite Alarms — Advanced

A Composite Alarm combines multiple alarms with AND/OR logic to reduce alert noise.

💡
Example: Only alert if BOTH CPU > 80% AND Network errors > 100. A CPU spike alone might not be a problem — but CPU spike + network errors together indicates real trouble.
COMPOSITE ALARM RULE
ALARM("EC2-HighCPU-Alarm") AND ALARM("EC2-NetworkErrors-Alarm")

CloudWatch Dashboards

Creating a Production Dashboard

📊
Dashboards are custom pages with widgets (line graphs, number displays, text) showing metrics from any AWS service or region. They are real-time and auto-refresh.

Recommended Widgets for a DevOps Dashboard:

  • 📊 EC2 CPU Utilization (line graph) — all instances
  • 📊 ALB Request Count per Target (line graph)
  • 📊 ALB 5XX Error Rate (line graph)
  • 📊 RDS Read/Write Latency (line graph)
  • 🔢 Active EC2 Instance Count (number widget)
  • 🔢 Lambda Error Count (number widget)
  • 📊 SQS Queue Depth (line graph)
  • 🔔 Alarm Status Panel (alarm list widget)
💰
Cost: First 3 dashboards with up to 50 metrics are free. After that: $3/dashboard/month.

CloudWatch Events / Amazon EventBridge

Automated Responses to Infrastructure Changes

CloudWatch Events (now evolved into Amazon EventBridge) lets you trigger automated actions when AWS resource state changes.

Event Sources (Triggers):

  • EC2 state change: running → stopped
  • Auto Scaling: instance launched/terminated
  • CloudTrail: specific API call made
  • Scheduled: run every 5 minutes (cron)
  • CodePipeline: deployment started/failed

Targets (Actions):

  • Trigger a Lambda function
  • Send to SQS queue
  • Publish to SNS topic
  • Start an SSM Automation runbook
  • Start a CodePipeline pipeline
💡
Example: EC2 instance stops unexpectedly → EventBridge triggers Lambda → Lambda sends Slack message to #incidents channel with instance ID and last CloudWatch metrics.

📚 Session Summary — CloudWatch Key Takeaways

  • CloudWatch is the central observability service — Metrics, Logs, Alarms, Dashboards, Events
  • EC2 does NOT send RAM/Disk metrics by default — install CloudWatch Agent for those
  • Alarms have 3 states: OK, ALARM, INSUFFICIENT_DATA. Alarms trigger SNS, ASG actions
  • Log Groups → Log Streams → Log Events. Always set retention policy to avoid runaway costs
  • Logs Insights: powerful SQL-like query language for analyzing log data
  • Metric Filters: pattern match log text → create a metric → create alarm on that metric
  • Composite Alarms: combine multiple alarms with AND/OR to reduce noise
  • EventBridge: trigger Lambda/SQS/SNS automatically when AWS state changes
  • Custom Metrics: publish any app data (orders/min, login failures) via CLI or SDK
