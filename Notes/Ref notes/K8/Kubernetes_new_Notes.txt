==> Kuberenets [k8s] :
         Kuberenets is an open source container orchestration technology for automating deployment ,scaling,and 
		  management of containeraized applications
   ->    Kuberenets is orginally developed by google and is now maintaned by cloud native computing foundation(CNCF)

==> Kuberenets Architecture :
 1)Master (Control Plane ) :
              Kuberenets master majorly runs with 4 components 
    1)API Server :
        ->    API serevr is the  main Managemnt point of the entire cluster.when we interact with  kubernetes cluster 
		       using the kubectl command we are actually communicating with the master API serevr.			   
        ->    API server is the only kubernetes component that connects to all other components 
		        API server is also responsible for authentication and authorization
	    ->    The API server also implements a watch mechanisam to watch for any required changes.this allows components
                such as the schedular and the controller manager to interact with the API server and try to match the
                desired state with the actual state.
   2) Etcd : 				
        etcd is a distributed,consistent key value store used to store the configuration data of the complete 
		kubernetes cluster .etcd reliabily stores the configuration data of the kubernetes cluster representing the
		state of the cluster at any given point of time (Ex:what nodes existing in the cluster,what pods should be
		running,which nodes they are running on etc.)
             etcdctl snapshot save -> used to take backup of entire kubernetes cluster data
			 etcd.io --> website of etcd
	3) Shedular :
             A schedular watches for any unschedule pods and binds them to the nodes
        ->   Shedular decides which node the pod has to be created according to the availability of the requested
             resources,affinity and anti-affinity specifications and other constrains.
			 
    4) Controller/Control-Manager :
     	     It is a deamon which runs a never ending core control loop (also known as controllers).Basically 
			 a controller watches the state of the cluster through the API serevr watch mechanisam,and when it gets 
			 notified it makes the necessary changes attempting to the current state towards the desired state.
	
        Examples : 1) Deployment
		           2) Replications/Replica set	
				   3) Stateful set
				   4) Deamon set ...etc

==> Pod Phases/Pod Lifecycle :
 
1.Pending :
   The pod has been accepted by the kubernetes cluster but one or more containers present in the pod have not yet been started.
2.Running :
          The pod has been bount to a node all of the containers are up and running
3.Succeeded :
   All the containers in the pod have terminated in the sucess and will not be restarted  
4.Failed :
  All the containers in the pod have terminated and atleast one container has terminated in failure i,e the container is
  exited in non zero status(error).
 5.Unknow :
   For some reason the state of the pod could not be obtained then the pod goes into unknown phase.This phase typically occurs
   due to an error in communicating with the node where the pod is running

==> Probes :
  Probes are the actions performed by kublet which provides health checks to monitor and check the state or the condtion of
   the pods
  -> probes are defined at the container level and we can define multiple probes inside our manifest file 

--> Configure probes:
   probes have a number of fields that we can use preciousily control the behaviour of probe checks
   1.Initial DelaySeconds :
       number of seconds after the container has started before the probe gets executed for the first time.
	   default value is 0 seconds
  2.periodseconds :
     how often to perform the probe.default value is 10 seconds
  3.timeoutseconds:
       number of seconds that the probe waits for a response before assuming failure.default value is 1 second
  4.successThreshold:
      minimum consecutive times for the probes to be consider successfull after having fail.default value is 1.
  5.FailureThreshold:
       when a probe check fails kubernetes will try failure threshold times before giving up.default value is 3.

==> Types of Probes :

1.Readiness Probe :
    Readiness probes are used to check weather the applications inside the container are ready and able to receive external 
	request.if the condition inside readiness probe fails applications are not allowed to serve any request.this way 
	kubernetes can prevent an application to recive request when it is still loading or too busy to process them properly.

2.Liveness Probe :
      Liveness probe works exactly like readiness probes but incase of failure it causes the container to be killed and 
      restarted so that it would return the application to its intial healthy state

3.Startup probe :
     startup probe was introduced in version 1.16.startup probe and liveness probe are both exactly the same in case of failure
     they cause the container to be restarted
  -> if both startup and liveness probes are configured for the pods kubernetes will execute startup probe first.if it succeeds
  then the liveness probe will be executed normally as configured.if the startup probes fails the pod is restarted and the
  cycle is repeate it is an extral layer of check for the pods.
  
apiVersion: v1
kind: Pod
metadata:
  name: probe
  labels:
	type: probe
spec:
  containers:
  - name: probe
    image: alpine
	ports:
	- containerPort: 80
	<probe_type>
	  <probe_action>
	  initialDelaySeconds: 0
      periodSeconds: 10
	  timeoutSeconds: 1
	  successThreshold: 1

==> Scheduling Pods :
             in general scheduling of pods is handle by kubernetes schedular.schedular ensures that the right node is selected
			 by checking the nodes capacity for CPU & RAM
	     -> However there are some scenarios where you want your pods to end upon specific nodes
	For EX :
	    1.when we want a pods to end up on a node with some particular resource availabe on it.
	    2.when we want to co-locate pods on particular nodes from the same availability zone
		3.when we want to co-locate a pod from one service with a pod from another service on the same node due to strong
		   dependency on each other.
	-> the three methods in kubernetes to schedule the pods manually are
                   1.Node Selector
                   2.Affinity and Anti-Affinity
                   3.Taints and Tolerations

1.Node Selector :
     NodeSelector is the simplest way of scheduling the pods to a particular node using its labels and defining them under
	 NodeSelector in the manifest file.

Syntax :
     nodeSelector:
	   <key>: <value>

kubectl label node <node_name> <key>=<value> --> To assaign a label to the node
kubectl getnodes --show-labels -->  to display all the labels of the node
	   
2.Affinity and Anti-Affinity :
     The Affinity greatly expands the node selector and there are two types of Affinity in kubernetes NodeAffinity and
	 PodAffinity
-> Affinity also provides soft and hard scheduling rules,if the soft rule is not met the schedular can still schedule a pod
   onto a specific other node
   Syntax :
   spec:
     affinity:
	   <affinity_type>
	      requiredDuringSchedulingIgnoredDuringExecution   (this the way to write hard limit)
  
   2 ways of assaign limits hardlink and softlink
  -> Hard Rule : requiredDuringSchedulingIgnoredDuringExecution 
  
  -> Soft Rule : preferedDuringSchedulingIgnoredDuringExecution 
 
--> Node Affinity :
     Similar to node selector node Affinity allows scheduling of pods to specific nodes ,we are using more expressions.
    synax :
   	 spec:
     affinity:
	   nodeAffinity:
	      requiredDuringSchedulingIgnoredDuringExecution
		    nodeSelectorTerms
			- matchExpressions:
			   - key: <key>
			   operator: In  
			   values:
			   - <value>
			   
apiVersion: v1
kind: Pod
metadata:
  name: na-nginx
  labels:
    app: nginx
spec:
  containers:
  - name: nginx-container
    image: nginx:latest
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 1
        preference:
          matchExpressions:
          - key: ec2
            operator: In
            values:
            - worker2			   

Pod Affinity and Pod Anti-Affinity :
    with pod Affinity and Anti-Affinity we can define weather a pod should or should not be scheduled on to a particular node
	based on labels of other pods already running on that node 
 
    synax :
   	 spec:
     affinity:
	   <podAffinity/podAntiAffinity>
	      requiredDuringSchedulingIgnoredDuringExecution
		  - labelSelector
			matchExpressions:
			   - key: <key>
			   operator: In

			   - <value>

Taints & Tolerations :
        Affinity is a property of pods that attracts them to a set of nodes.while the taints are the opposite.they allow a 
		node to repel a set of pods 
	-> Tolerations are applied to pods so that they are allowed to schedule on to nodes with matching taints
kubcetel taint nodes <node_name> <taint_key>=<taint_value>:<taint_effect> --> to taint a node with particular key and effect
kubectl taint nodes <node_name> ec2=taint:NoSchedule

kubcetel taint nodes <node_name> <taint_key>=<taint_value>:<taint_effect>-  --> to untaint a node 


Taint Effects:
1.NoSchedule
2.PreferNoSchedule
3.NoExecute

apiVersion: v1
kind: Pod
metadata:
  name: ns-nginx
  labels:
    app: nginx
spec:
  containers:
  - name: nginx-container
    image: nginx:latest
  tolerations:
  - key: "ec2"
    operator: "Equal"
    value: "taint"
    effect: "NoSchedule"

     -> Persistent Volumes can be created in 2 ways	  
	      1.static persistent volume[manually created by the administrator]
		  2.dynamic persistent volume [automatic] (storage classes)
1.static persistent volume[manually created by the administrator]

		PV --> PVC --> POD

            In dynamic volumes we configure storage classes to dynamically create persistent volumes.The main goal of storage
			class is to eliminate the need for administrators to pre-provisioned storage.here volumes are created dynamically
			on demand.developers can then request storage by specifying the storage class in pvc
		StorageClass -> PVC --> Pod	
 Persistent Volume Claim:
    to claim a persistent volume we use PVC.PVC is a way for a developer to request storage for the application

==> RBAC :
  RBAC is an approach in kubernetes used to add constrains for users,groups and serviceAccounts to acess kubernets 
   resources.RBAC basically adds security to kubernetes cluster and we can apply it for a specific namespace or to 
   the totally cluster.RBAC uses rbac.authorization.k8s.io.API group
   
1.Subject :
    subject is the entity that needs access to the cluster it could be user or a group or a service account
2.Resource:
   Resource is the kubernetes object that a subject wants to access,it could be pods,deployments,services etc
3.Verbs :
   Verbs are the actions that a subject can perform on resources it could be list,delete,create,watch etc

==> what is role and clusterrole ?
 Role :
          In a Role,the rules are applicable to a single namespace 
		  
 ClusterRole :account to have acess the whole cluster	 
	            A ClusterRole is cluster-wide, so the rules are applicable to more than one namespace.
	             ClusterRoles can define rules for cluster-scoped resources (such as nodes) as well
				 
==> What is RoleBinding and ClusterRoleBinding ?

 RoleBinding :
       A RoleBinding grants permissions within a specific namespace.A RoleBinding may reference any Role in the same namespace.
	   Alternatively, a RoleBinding can reference a ClusterRole and bind that ClusterRole to the namespace of the RoleBinding	

 ClusterRoleBinding : outside namespace in the cluster
           ClusterRoleBinding grants that access cluster-wide.If you want to bind a ClusterRole to all the namespaces 
		   in your cluster, you use a ClusterRoleBinding.

==>What does Helem chart contains/ what are the components of the helem chart ?
    1. .helem ignore 
         .helmignore: This holds all the files to ignore when packaging the chart. Similar to .gitignore.
		 
    2. Chart.yaml: 
	      This is where you put all the information about the (helem)chart you are packaging. So,for example, your version
		  number,etc. This is where you will put all those details.(inside this file it has apiversion,name,descrption,type,
		    appversion)
    3. Values.yaml: 
	      This is where you define all the values you want to inject into your templates. If you are familiar with
		  terraform think of this as helms variable.tf file.
		  where we pass on necessary required values here(like replicacount,image,imagePullSecrets,service,resources)
    4. Charts:
       	This is where you store other charts that your chart depends on. You might be calling another chart that your
		chart need to function properly.(any dependency  of helem chart we have here)
    5. Templates: 
	      This folder is where you put the actual manifest you are deploying with the chart. For example you might be
		  deploying an nginx deployment that needs a service, configmap and secrets. You will have your deployment.yaml,
		  service.yaml, config.yaml and secrets.yaml all in the template dir. They will all get their values from
		  values.yaml from above.
		  --> you will have all manifest files (volumes,secrects,configmaps,deployment.yamal,service,ingress we will keep all 
		      those in under this template folder)
    6. _hepers.tpl: 
	     This is file is used to create a templates which we can refer in the manifest files.

===> ARCHITECTURE 
--> HELEM 2:
    1.  Helm 2 is a client-server architecture with the client called helm and the server called Tiller. 
	2. The client is a CLI that users interact with to perform different operations like install, upgrade, and delete.
	3. The client interacts with Tiller and the chart repository. 
	4. Tiller interacts with the Kubernetes API server. 
	5 It renders Helm template files into Kubernetes manifest files, which it uses for operations on the Kubernetes cluster
     	through the Kubernetes API
		
--> HELEM 3 :
    1. Helm 3 has a client-only architecture with the client still called helm.
	2. It operates similar to the Helm 2 client, but the client interacts directly with the Kubernetes API server. 
	3. The in-cluster server Tiller is now removed.
