Absolutely. For Tomcat training, I would teach the directory structure from a DevOps/production troubleshooting perspective, not just as a list of folders. Students should understand what each directory contains, who uses it, what changes there, and what happens when something goes wrong.

Apache Tomcat Directory Structure
4

A typical Tomcat installation looks like:

/apache-tomcat/
│
├── bin/
├── conf/
├── lib/
├── logs/
├── temp/
├── webapps/
├── work/
└── webapps.dist/     (Ubuntu/Debian installations may have this)

The most important directories for DevOps engineers are:

bin/
conf/
webapps/
logs/
lib/
work/
temp/
1. First understand CATALINA_HOME vs CATALINA_BASE

This is one of the most important concepts to teach.

CATALINA_HOME

CATALINA_HOME points to the Tomcat installation directory.

Example:

/opt/tomcat

It contains Tomcat's binaries and core files.

You can check:

echo $CATALINA_HOME
CATALINA_BASE

CATALINA_BASE represents the runtime/instance directory.

Example:

/opt/tomcat-instance

It contains:

conf/
logs/
webapps/
work/
temp/
Why are both useful?

Suppose you want to run two Tomcat instances using the same Tomcat installation:

Tomcat installation
        |
        +---- CATALINA_HOME
        |
        +---- Instance 1
        |       └── CATALINA_BASE
        |
        +---- Instance 2
                └── CATALINA_BASE

This is useful when running multiple applications or environments on the same server.

For beginners, simply remember:

CATALINA_HOME = Tomcat software
CATALINA_BASE = Tomcat runtime instance

2. bin/ — Tomcat Executables and Startup Scripts
bin/
├── startup.sh
├── shutdown.sh
├── catalina.sh
├── version.sh
├── setclasspath.sh
├── configtest.sh
└── daemon.sh

This is the directory students will frequently use while managing Tomcat manually.

Important files
startup.sh

Starts Tomcat.

./startup.sh

or:

$CATALINA_HOME/bin/startup.sh

Typical output:

Using CATALINA_BASE:   /opt/tomcat
Using CATALINA_HOME:   /opt/tomcat
Using CATALINA_TMPDIR: /opt/tomcat/temp
Using JRE_HOME:        /usr/lib/jvm/java-11-openjdk
shutdown.sh

Stops Tomcat.

./shutdown.sh
catalina.sh

This is one of the most important scripts.

startup.sh and shutdown.sh internally use catalina.sh.

You can run:

./catalina.sh start
./catalina.sh stop
./catalina.sh run

The difference is important.

./catalina.sh start

starts Tomcat in the background.

./catalina.sh run

runs Tomcat in the foreground.

Excellent troubleshooting example

If Tomcat is failing to start:

./catalina.sh run

This allows students to see startup errors directly in the terminal.

version.sh

Shows Tomcat and Java information.

./version.sh

Useful during troubleshooting.

3. conf/ — Most Important Configuration Directory

This is probably the #1 directory to focus on during Tomcat training.

conf/
├── server.xml
├── web.xml
├── context.xml
├── tomcat-users.xml
├── catalina.properties
├── logging.properties
└── jaspic-providers.xml
4. server.xml — Critical Configuration

Location:

$CATALINA_HOME/conf/server.xml

This is Tomcat's primary server configuration file.

Students should understand:

server.xml
    |
    +-- Server
         |
         +-- Service
              |
              +-- Connector
              |
              +-- Engine
                   |
                   +-- Host
                        |
                        +-- Context

A simplified configuration:

<Server>
    <Service name="Catalina">


        <Connector port="8080"
                   protocol="HTTP/1.1"/>


        <Engine name="Catalina">


            <Host name="localhost"
                  appBase="webapps">


            </Host>


        </Engine>


    </Service>
</Server>
5. Tomcat Port — Connector

Students frequently need to find the Tomcat port.

Example:

<Connector port="8080"
           protocol="HTTP/1.1"
           connectionTimeout="20000"
           redirectPort="8443" />

Here:

8080 → HTTP
8443 → HTTPS redirect/secure connector

If someone asks:

"Tomcat is running, but I cannot access the application."

Check:

grep -n "Connector" conf/server.xml

or:

grep -n "8080" conf/server.xml

Then check whether the port is listening:

ss -lntp | grep 8080
6. HTTPS Configuration

Tomcat can also have an HTTPS connector.

Example:

<Connector
    port="8443"
    protocol="org.apache.coyote.http11.Http11NioProtocol"
    SSLEnabled="true"
    scheme="https"
    secure="true"
    keystoreFile="/opt/tomcat/conf/keystore.jks"
    keystorePass="changeit" />

Students should understand:

Client
   |
   | HTTPS :443
   ↓
Load Balancer / Nginx
   |
   | HTTP :8080
   ↓
Tomcat

In production, TLS termination is often done at the load balancer or reverse proxy rather than directly in Tomcat.

7. web.xml

Location:

conf/web.xml

This is the global deployment descriptor.

It defines default web application behavior.

Students should understand the distinction:

conf/web.xml
        ↓
Global/default configuration


WEB-INF/web.xml
        ↓
Application-specific configuration

Don't confuse these two.

8. context.xml

Location:

conf/context.xml

It contains default Tomcat Context configuration.

A Context represents a deployed web application.

For example:

Tomcat
   |
   +-- Host
        |
        +-- Context
             |
             +-- Application

You may also see:

conf/Catalina/localhost/

This directory is particularly important for application-specific context configuration.

Example:

conf/
└── Catalina/
    └── localhost/
        └── myapp.xml

This can define where an application is deployed from.

9. tomcat-users.xml

Location:

conf/tomcat-users.xml

This can define Tomcat users and roles.

Example:

<role rolename="manager-gui"/>
<user username="admin"
      password="password"
      roles="manager-gui"/>

This is commonly used when configuring Tomcat Manager.

Important security point for students

Never teach students to use:

password="password"

in production.

Also explain that exposing Tomcat Manager directly to the internet is a security risk.

10. catalina.properties

Location:

conf/catalina.properties

Contains Tomcat properties such as:

common.loader
server.loader
shared.loader

It also controls class-loading-related behavior.

This becomes more important when students encounter:

ClassNotFoundException
NoClassDefFoundError

or dependency conflicts.

11. logging.properties

Location:

conf/logging.properties

Controls Tomcat's Java logging configuration.

Students should understand:

Application
    ↓
Tomcat logging
    ↓
logs/
12. webapps/ — Where Applications Are Deployed

This is the second most important directory.

webapps/
├── ROOT/
├── manager/
├── host-manager/
└── myapp/

Applications are deployed here.

For example:

webapps/
└── myapp/
    ├── index.jsp
    ├── WEB-INF/
    │   ├── web.xml
    │   ├── classes/
    │   └── lib/
    └── META-INF/
13. WAR File Deployment

Suppose you have:

myapp.war

Copy it into:

cp myapp.war /opt/tomcat/webapps/

Tomcat automatically deploys it.

You may then see:

webapps/
├── myapp.war
└── myapp/

Tomcat extracts the WAR:

myapp.war
    ↓
myapp/

The application URL normally becomes:

http://server-ip:8080/myapp
14. Why is ROOT special?

Suppose:

webapps/
└── ROOT/

Then:

http://server-ip:8080/

points to the ROOT application.

But:

webapps/
└── myapp/

would normally be:

http://server-ip:8080/myapp

This is a very useful concept for students.

15. WEB-INF — Very Important Application Directory

Inside an application:

myapp/
├── index.jsp
├── CSS/
├── JS/
└── WEB-INF/
    ├── web.xml
    ├── classes/
    └── lib/

WEB-INF is special.

A client cannot directly access resources under:

WEB-INF/

For example:

http://server:8080/myapp/WEB-INF/web.xml

should not be directly served to the client.

16. WEB-INF/classes/

This contains compiled Java classes.

Example:

WEB-INF/
└── classes/
    └── com/
        └── company/
            └── MyServlet.class

If an application has:

ClassNotFoundException

students should understand that class-loading and this directory may be relevant.

17. WEB-INF/lib/

This contains application-specific JAR files.

Example:

WEB-INF/lib/
├── spring-core.jar
├── mysql-connector.jar
├── servlet-api.jar
└── application.jar

This is extremely important when troubleshooting:

ClassNotFoundException
NoClassDefFoundError
dependency conflicts
18. logs/ — Extremely Important for DevOps

This is probably the most important directory during production troubleshooting.

logs/
├── catalina.out
├── catalina.2026-08-14.log
├── localhost.2026-08-14.log
├── localhost_access_log.2026-08-14.txt
└── manager.2026-08-14.log

Names can vary depending on the Tomcat version and logging configuration.

19. catalina.out

One of the first places students should check when Tomcat has problems.

tail -f logs/catalina.out

For example:

java.lang.OutOfMemoryError: Java heap space

or:

Address already in use

or:

SEVERE: Error starting component

These logs immediately give clues.

20. Access Logs

Example:

localhost_access_log.2026-08-14.txt

These tell you about HTTP requests.

Example:

10.10.10.10 - - [14/Aug/2026:10:10:10 +0000] "GET /myapp HTTP/1.1" 200 1234

Students should understand:

GET /myapp HTTP/1.1
       ↓
requested URL


200
 ↓
HTTP response status

Common statuses:

200 → Success
301 → Redirect
302 → Redirect
400 → Bad Request
401 → Unauthorized
403 → Forbidden
404 → Not Found
500 → Internal Server Error
502 → Bad Gateway
503 → Service Unavailable
21. temp/
temp/

Tomcat uses this for temporary files.

For example:

temp/

may contain temporary processing files.

Usually students should not manually modify files here.

If troubleshooting strange temporary-file issues, you may inspect it.

22. work/

This directory is very important to understand.

work/
└── Catalina/
    └── localhost/
        └── myapp/

Tomcat uses work/ for generated/compiled JSP-related files and other runtime working data.

For JSP:

index.jsp
   ↓
Tomcat Jasper
   ↓
Generated Java servlet
   ↓
Compiled class
   ↓
work/

So if a JSP behaves strangely, work/ can sometimes be relevant.

23. lib/

Location:

lib/

Contains libraries available to Tomcat itself / shared class loading.

Example:

lib/
├── ...
└── custom-library.jar

Important distinction:

Tomcat-wide libraries
        ↓
$CATALINA_HOME/lib

versus:

Application-specific libraries
        ↓
webapps/myapp/WEB-INF/lib

This is important when teaching Java class loading.

TOMCAT

25. The 5 Paths Students Must Remember

For a DevOps engineer, I would tell students:

1. bin/

Question: How do I start/stop Tomcat?

cd /opt/tomcat/bin
./startup.sh
./shutdown.sh
2. conf/server.xml

Question: Where is the Tomcat port configured?

grep -n "Connector" /opt/tomcat/conf/server.xml
3. webapps/

Question: Where is my application deployed?

ls -lh /opt/tomcat/webapps/
4. logs/

Question: Why is my application/Tomcat failing?

tail -f /opt/tomcat/logs/catalina.out
5. work/

Question: Where does Tomcat keep generated runtime/JSP working files?

ls -R /opt/tomcat/work/
26. Production Troubleshooting Flow

This is the real-time scenario I recommend giving students.

Scenario

Developer says:

"My application is deployed, but I cannot access it."

Don't immediately restart Tomcat.

Teach students to follow this sequence:

Step 1 — Check Tomcat process
ps -ef | grep tomcat

or:

systemctl status tomcat
Step 2 — Check the port
ss -lntp | grep 8080

If nothing is listening:

Tomcat may not be running
OR
Tomcat failed during startup
Step 3 — Check server.xml
grep -n "Connector" /opt/tomcat/conf/server.xml

Confirm:

8080
Step 4 — Check application deployment
ls -lh /opt/tomcat/webapps/

Look for:

myapp.war
myapp/
Step 5 — Check logs
tail -100 /opt/tomcat/logs/catalina.out

Search for errors:

grep -i "error" /opt/tomcat/logs/catalina.out
grep -i "exception" /opt/tomcat/logs/catalina.out
Step 6 — Test locally
curl http://localhost:8080/

Then:

curl -I http://localhost:8080/myapp

This helps separate:

Tomcat problem
        vs
Network / Load Balancer / Firewall problem
27. A Very Good Classroom Exercise

Give students this structure:

/opt/tomcat/
├── bin/
├── conf/
├── lib/
├── logs/
├── temp/
├── webapps/
└── work/

Ask them to perform:

cd /opt/tomcat
Exercise 1

Find Tomcat version:

./bin/version.sh
Exercise 2

Find configured port:

grep -n "Connector" conf/server.xml
Exercise 3

List deployed applications:

ls -lh webapps/
Exercise 4

Watch logs:

tail -f logs/catalina.out
Exercise 5

Find errors:

grep -Ri "error" logs/
Exercise 6

Check which process owns port 8080:

sudo ss -lntp | grep 8080
Exercise 7

Deploy a WAR:

cp myapp.war webapps/

Then:

ls -lh webapps/

Wait for Tomcat to extract it:

myapp.war
myapp/

Then test:

curl http://localhost:8080/myapp
28. Simple Mental Model for Students

Give them this rule:

             TOMCAT
                |
      ┌─────────┼──────────┐
      ↓         ↓          ↓
     bin       conf      webapps
      |          |          |
   START       CONFIG      APP
   STOP        PORT        WAR
      |          |          |
      └──────────┼──────────┘
                 ↓
               logs
                 |
             TROUBLESHOOT

And remember:

BIN → Manage Tomcat
CONF → Configure Tomcat
WEBAPPS → Deploy applications
LOGS → Troubleshoot
LIB → Libraries
WORK → Runtime/generated files
TEMP → Temporary files

For a DevOps/Tomcat training session, I would spend the most time on bin/, conf/server.xml, conf/Catalina/localhost/, webapps/, WEB-INF/, and logs/, because these are the paths students will repeatedly use in deployment, troubleshooting, and production support.
