DNS Fundamentals — Teach This First!

📖 Analogy — Phone Book for the Internet

DNS is the internet's phone book. You remember names (google.com), not phone numbers (142.250.64.14). DNS translates human-friendly domain names into machine-friendly IP addresses. Without DNS, you'd need to memorize the IP address of every website — Route 53 is AWS's managed DNS service that does this translation reliably and at massive scale.

How DNS Resolution Works — Step by Step

You type: www.nimbuswiztech.com in your browser Step 1: Browser checks LOCAL CACHE → not found ↓ Step 2: Browser asks OS DNS resolver (your ISP or 8.8.8.8 - Google DNS) ↓ Step 3: Recursive resolver asks ROOT DNS servers (13 clusters worldwide) "Who handles .com domains?" ↓ Step 4: Root says → "Ask .COM TLD servers (Verisign)" ↓ Step 5: TLD (.com) servers say → "Ask ns-123.awsdns-45.net" (This is Route 53's nameserver for nimbuswiztech.com) ↓ Step 6: Route 53 nameserver responds → "www.nimbuswiztech.com = 54.201.11.22" ↓ Step 7: Browser connects to 54.201.11.22 → loads the website! ✅ Total time: 50-200ms (first visit, then cached for TTL duration)

DNS Record Types — The Essential Ones

Record TypePurposeExample
A RecordMaps domain name → IPv4 addressapp.example.com → 54.201.11.22
AAAA RecordMaps domain name → IPv6 addressapp.example.com → 2001:0db8::1
CNAME RecordMaps domain name → another domain name (alias). Cannot be used for root domain.www.example.com → app.example.com
MX RecordMail server for the domainexample.com → mail.example.com priority 10
TXT RecordText information — used for domain verification (Google, SSL), SPF recordsv=spf1 include:amazonses.com ~all
NS RecordName Servers responsible for this zonens-1.awsdns-10.org
SOA RecordStart of Authority — admin info for the zoneAuto-created by Route 53
ALIAS RecordAWS-specific extension of CNAME. Can point to AWS resources at root domain level. Free queries.example.com → ALB-12345.ap-south-1.elb.amazonaws.com
⚠️
Key Difference — ALIAS vs CNAME: CNAME cannot be used at the root domain (naked domain). You CAN'T do example.com CNAME alb.amazonaws.com. You CAN do example.com ALIAS alb.amazonaws.com. This is why AWS created the ALIAS record type — use it for ALBs, CloudFront, S3 websites.

Hands-On: Create Hosted Zone & DNS Records (Step-by-Step)

Lab 1: Create a Hosted Zone and Point to an EC2 Instance

1
Create a Public Hosted Zone
  • Route 53 → Hosted zones → Create hosted zone
  • Domain name: example.com (use your actual domain)
  • Type: Public hosted zone
  • Create → Route 53 creates the zone with NS and SOA records automatically
  • Note the 4 NS record values: ns-xxx.awsdns-xx.com / .net / .org / .co.uk
2
Update Nameservers at Your Domain Registrar
  • Go to your domain registrar (GoDaddy, Namecheap, etc.)
  • Find "Nameservers" setting for your domain
  • Replace existing nameservers with the 4 NS values from Route 53
  • Propagation takes 24-48 hours globally (for production domains)
ℹ️
If you registered the domain IN Route 53: The nameservers are already configured automatically — skip this step.
3
Create an A Record Pointing to EC2
  • In the hosted zone → Create record
  • Record name: app (creates app.example.com)
  • Record type: A
  • Value: 54.201.11.22 (your EC2 Elastic IP)
  • TTL: 300 (5 minutes — clients cache for this long)
  • Create records
4
Create an ALIAS Record for an ALB (Root Domain)
  • Create record → Record name: (leave blank for root domain example.com)
  • Record type: A
  • Toggle on: Alias
  • Route traffic to: Alias to Application and Classic Load Balancer
  • Region: ap-south-1 → Select your ALB
  • Create records
5
Test the DNS Resolution
nslookup app.example.com dig app.example.com +short curl -I http://app.example.com

Route 53 Routing Policies — The Most Important Section

7 Routing Policies — Teach Each with a Real Use Case

1. Simple Routing

What: One record, one or more IP values. Route 53 returns a random IP from the list.
Use case: Single server, no health checks. Most basic setup.
Example: app.example.com → 54.201.11.22

2. Weighted Routing

What: Distribute traffic across multiple resources by percentage weight.
Use case: A/B testing, Blue/Green deployments, gradual migration.
Example: Version 1 (weight 90) = 90% traffic. Version 2 (weight 10) = 10% traffic.

WEIGHTED ROUTING EXAMPLE
Record 1: app.example.com → 54.201.11.22 Weight: 90 Record 2: app.example.com → 54.201.11.99 Weight: 10 # Route 53 sends 90% of queries to Record 1, 10% to Record 2

3. Latency-Based Routing

What: Route users to the AWS region with the lowest latency from their location.
Use case: Global applications — users in India get routed to ap-south-1, US users to us-east-1.
Example: Two EC2s — one in Mumbai, one in N.Virginia. Route 53 measures latency and routes accordingly.

💡
Route 53 measures latency using a database it maintains from edge locations globally — it doesn't ping your user every time.

4. Failover Routing (Active-Passive)

What: Primary record handles all traffic. If health check fails → Route 53 automatically routes to secondary.
Use case: Disaster Recovery — primary production server, secondary DR server.
Requires: Health check configured on the primary record.

Primary: 54.201.11.22 (Healthy ✅)
→
All traffic → Primary
Primary: 54.201.11.22 (FAILS ❌)
→
Route 53 detects via health check
→
All traffic → Secondary: 54.201.99.11

5. Geolocation Routing

What: Route based on the geographic location of the USER (country, continent, state/province for US).
Use case: Serve localized content, comply with data residency laws, block certain geographies.
Example: Indian users → India server, EU users → Frankfurt server, US users → Virginia server. Default record for everyone else.

⚠️
Geolocation vs Latency: Geolocation is based on where the user is. Latency is based on which server is fastest for the user. They often agree, but not always (e.g., a user in India on a satellite connection might get lower latency from a closer server even if they're geographically in India).

6. Geoproximity Routing (Traffic Flow Only)

What: Route based on geographic location of users AND resources. You can adjust the bias to shift more/less traffic to a resource.
Use case: When you want to gradually move traffic from one region to another — increase bias on the new region to attract more traffic.
Requires: Route 53 Traffic Flow (visual policy editor) — $50/policy/month.

7. Multi-Value Answer Routing

What: Returns up to 8 healthy IP addresses in random order. Each IP has an associated health check.
Use case: Simple client-side load balancing across multiple healthy servers. Not a substitute for a proper LB, but simple alternative.
Benefit over Simple: Unhealthy IPs are automatically removed from the response.

Route 53 Health Checks

What are Health Checks?

Route 53 sends periodic requests to your endpoints to check if they're healthy. If unhealthy, DNS routing policies (Failover, Multi-Value) respond accordingly.

Health Check Types:

  • HTTP/HTTPS/TCP — checks a specific endpoint (most common)
  • CloudWatch Alarm — healthy if a CloudWatch alarm is in OK state
  • Calculated Health Check — combines multiple child health checks (OR/AND logic)

Health Check Configuration:

  • Protocol: HTTP/HTTPS/TCP
  • Endpoint IP or domain
  • Port and path (e.g., /health)
  • Expected status code (200)
  • Interval: 30 sec (standard) or 10 sec (fast — $0.01/check/month extra)
  • Failure threshold: 3 (fails 3 checks → unhealthy)
💡
Health Check IPs: Route 53 sends health check requests from multiple AWS edge locations globally. Your security group/firewall must allow traffic from Route 53 health checker IP ranges (ip-ranges.amazonaws.com, service: ROUTE53_HEALTHCHECKS).
🔬 Lab 2: Create a Health Check + Failover Routing Policy
Demonstrate automatic DNS failover — Route 53 switches traffic when primary fails
  1. Launch two EC2 instances — one in ap-south-1 (Primary), one in us-east-1 (Secondary). Install Nginx on both.
  2. Create Health Check on Primary:
    • Route 53 → Health checks → Create health check
    • Name: primary-server-health
    • Monitor: Endpoint → IP address → Primary EC2 IP → Port 80 → Path: /
  3. Create Failover record — PRIMARY:
    • Create record → app.example.com → Type A → Primary EC2 IP
    • Routing policy: Failover → Record type: Primary
    • Associate health check: primary-server-health
  4. Create Failover record — SECONDARY:
    • Create record → app.example.com → Type A → Secondary EC2 IP
    • Routing policy: Failover → Record type: Secondary
    • No health check on secondary (always fallback)
  5. Test failover: Stop the primary EC2 → Watch health check turn UNHEALTHY → Run nslookup app.example.com every 30 seconds → IP changes to secondary within 30-60 seconds!

📚 Session Summary — Route 53 Key Takeaways

  • DNS = translates domain names to IP addresses. Route 53 is AWS's managed DNS service
  • Key record types: A (domain→IPv4), AAAA (→IPv6), CNAME (→another domain), ALIAS (→AWS resource, even at root), MX (mail), TXT (verification)
  • ALIAS vs CNAME: Use ALIAS for AWS resources, especially at root domain. Cannot use CNAME at root domain
  • Public Hosted Zone = internet-facing DNS. Private Hosted Zone = internal VPC DNS only
  • 7 Routing Policies: Simple, Weighted (A/B test), Latency (performance), Failover (DR), Geolocation (user's country), Geoproximity (bias shifting), Multi-Value (client-side LB)
  • Health Checks: Route 53 monitors endpoints. Failover routing automatically reroutes when primary fails
  • Domain Registration: Buy domains directly in Route 53 — auto-configures nameservers
  • TTL: Lower TTL = faster DNS changes propagate. Higher TTL = lower cost (fewer resolver queries)
